# Description
This file shows the structure and general rules of how to structure and work with 801_26_lokal-llm and 2026 Lokal LLM documentation.

---

## General rules for documentation

Each "project" has a documentation foulder matching the structure of the project itself.
Each code file in the project should have a corresponding documentation file in the documentation folder. 
For example, if there is a code file called "data_preprocessing.py" in the project, there should be a documentation file called "data_preprocessing.md" in the documentation folder.

### Structure of documentation files
1. **Firstly start with a description of the file and its purpose. Here you answer 3 questions:**
   - What does the file do?
   - How does it do it? Include references to external files/dependencies if necessary.
   - Why is it important for the project?

2. **Then if there are any classes answer the following points:**
   - What does the class do?
   - How does it do it? Include references to external files if necessary.
   - What are the inputs and outputs of the class?
   - Inheretance?
   - Attributes?

3. **Functions:**
   - **Purpose** / Explanation
   - **Arguments** (with data types explanation)
   - **Return values** (with data types and explanation))

--- 

## Commenting in the code

**The comments and how they are structured should appear in the following way:**

1. **Short explanation** of the code file at the top of the file.

2. **Possibly a "todo"** section or problems near the top of the file.

3. **Structuring of the code into sections** with headers and comments explaining the purpose of each section.

3. **Explaining the functions**, contex-based.
